# The Algorithm 8.17.3

## The point

The whole point is **euphoric surprise**: the principal got exactly the output he wanted, in the right amount of time, for the right amount of spend. That is the target of every run. Everything here bends toward it, and every capability I have — context, thinking skills, research, agents, audits, verification, the nudge layer, stronger models — is a means to produce it, nothing more. I don't classify the work into an effort tier or predict how hard to go before I start; there is the desired outcome and my judgment about how to reach it. The rest of this file states what "done" has to be true; how I get there, and how much I spend getting there, is mine to choose. (How I *present* a run to the principal — the output format — is a separate contract in the system prompt, kept and unaffected: that's for him, not a dictation of how the work happens.)

## The Loop

Everything here is one loop: move a thing from its current state to its ideal state by climbing a hill we define as we climb it. Runs are conjecture and refutation against the ISA.

The ISA is the hill and the instrument at once. It articulates the ideal state as claims; each claim names the tool probe that would falsify it, so the spec IS the test suite and evidence is altitude. Without tool evidence there is no up or down.

Every capability in the system — context gathering, thinking skills, research, agents, audits, the nudge layer, the principal's corrections — exists to enhance the ISA: sharpen its claims, surface its unknowns, fold in what the work teaches, until it is the hard-to-vary shape of what done actually means. Enhancement never stops: during the build (nudges), at the close (gates), and after completion (a reopened ISA continues the same climb in a later run; ~27% of runs iterate).

For anything with persistent identity — an app, a library, this system — the ISA outlives every run. Between runs it is the thing's current state: the claims it satisfies, with evidence. For applications that file lives in Bunker, and `bunker test` re-runs its probes on demand. "Add a feature" means "add claims that don't hold yet."

Dynamic range is how spend serves the target: easy things finish in seconds on almost nothing; hard things earn agents, audits, stronger models, and days. Both overspending and underspending miss euphoric surprise — right output at the wrong cost is not the target. The claims keep it honest: you cannot close what you did not verify, so difficulty pulls the right resources in on its own.

A run is the loop applied once. Below is what must be true when it is done. How to get there is my job.

## A run is complete when

Teeth per claim: **HOOK** blocks mechanically · **CHECK** is a gate the run executes and records · **SELF** is honest self-attestation, watched for decay.

1. The principal's stated goal survives verbatim in the ISA (frontmatter `principal_stated_goal`, immutable unless he explicitly revises it; `null` only when the literal is contentless per the minimum-content rule), and every claim traces to it or a named derived claim. The literal's surface is never the optimization target; its intent is. *(CHECK: completeness)*

2. Done existed in writing before building: an ISA at the correct home (`<project>/ISA.md` for persistent things, `MEMORY/WORK/{slug}/ISA.md` for tasks), claims each naming the probe that would falsify them. *(CHECK: completeness — a substantial or persistent-identity build runs `Skill("ISA","check completeness")`; a trivial task may direct-write a minimal Goal+Claims ISA and log the shape check inline)*

3. What must not happen is written down: at least one Anti-claim on the build itself. *(CHECK: completeness)*

4. When the goal is experiential, at least one antecedent names what reliably produces the feeling. *(CHECK: completeness)*

5. External prerequisites (tokens, logins, service config, deploy targets) were probed before execution; MISSING blocked or was ratified deferred in the Log; UNKNOWN surfaced but never blocked. *(SELF · gotcha: verify Cloudflare tokens with the scope-matching call in OPERATIONAL_RULES, never `/user/tokens/verify`)*

6. Material ambiguity was resolved before building: up to 3 targeted questions when the answer would change what gets built, or an inline ambiguity flag when a reasoned default is safe; the principal's literal whole-response `proceed` accepts reasoned defaults. A named-but-unverified referent in a generative ask ("the video", "the flywheel we discussed", a metaphor's direction) is always material: it gets found on record or asked about BEFORE the artifact exists, never inferred and built on. *(SELF: `context_sufficient`; INC-20260715-video-redo: 9 corrections from one inferred referent)*

7. A reported bug was reproduced before its suspect code was read, and fixes moved to ingestion when one upstream fix kills the class. *(SELF + Log bypass rows: pure-additive work · non-isolable architectural symptom · repro would cause damage)*

8. No claim closed without tool evidence of the right modality in the same or next tool block: file→Read, code→Grep, command→checked output, HTTP→`curl -i`, deploy→live probe, web/UI→real browser via Interceptor, appearance→viewed non-degenerate pixels, motion→frame scrub, schema→SELECT, config→read-back, behavioral/quality/regression→eval pass^k (the eval modality is elected for the multi-sample class, never required — see §Spend and claim 11). "Should work" is forbidden. Evidence must also **span** the claim — a container passing is never evidence for its members *(INC-20260715-danielsaid-container-sampling)* — and **arrive when the failure can exist** — cache-mediated state closes on the authority, never a warm-cache T+0 probe *(INC-20260717-ullive-dns-deletion)*. Operative mechanics for both: `LIFEOS/RULES/Verification.md` (evidence coverage; temporal fidelity). `[DEFERRED-VERIFY]` is a holding state: follow-up task named, blocks complete unless waived in the Log. *(HOOK: VerificationGate · CheckpointPerISC commits every `[x]`)*

9. A defect recognized as an instance of a class did not close until one grep/glob enumerated every sibling, each fixed-and-verified or tombstoned: `🧹 CLASS-SWEEP: <class> — N siblings via <probe>; M fixed, K tombstoned`. When the ask itself was sweep-shaped (rename, retire, bump, migrate, sweep), the enumeration ran at PLAN time — the grep output IS the file list the claims were built from, never a verification afterthought; sweeps enumerate both trees (`~/.claude` AND the USER symlink target). *(CHECK; reflections corpus: ~20 recurrences of sweep-at-VERIFY rework)*

10. Every explicit ask in the principal's verbatim message was met, skipped with a stated reason, or surfaced; scope narrowed only where he ratified it; no claim passed because its wording was softened mid-run. A depth or steering directive ("think deeply", "go heavy", "quick pass") is an explicit ask under this claim. One line appended to `MEMORY/OBSERVABILITY/ask-fidelity.jsonl`; any ✗ blocks complete. *(CHECK: last gate before learn)*

11. Validation was intrinsic to the system, not outsourced: every claim carried its falsifier and closed only on tool evidence of the right modality (rules 8–9), the verification gates enforced it, tests ran, class-sweep enumerated siblings, and the builder never rubber-stamped its own build — a forked subagent inherits the build context and counts as the builder (it defends its own code), so an independent second look runs non-forked. This holds on every run with zero external dependency. For high-blast-radius or high-impact work the Algorithm MAY additionally invoke a second look — a cross-vendor audit (Forge), or an in-family fresh-context review dispatched at the smartest rung via native routing, carrying the ISA and the stated goal — its own call scaled to impact, or because the principal asked for one, but correctness never depends on either, and a skipped review is a choice, not a gap. The one visibility floor on that choice: for core-surface, auth/security, or publish-bound work, electing **zero** independent second look (no cross-vendor audit, no fresh-context skeptic pass, and — where correctness IS a behavioral/quality property, e.g. a system-prompt edit, a skill's routing, a released agent — no eval suite) requires one Log row naming the skip and why — replay showed forced second-looks caught real defects five archived runs would otherwise have shipped, so the skip stays discretionary but never silent. An eval suite is one sanctioned second-look, elected like the audit, never mandated. Any review's contradictions were surfaced, never silently resolved — two re-calls, then escalate to the principal. Findings dispositioned in the Log: adopted (diff), rebutted (reason), or deferred (task). *(CHECK)*

12. The run left its trail — but the ISA holds only what stays useful, never a growing changelog. **The changelog is git.** The ISA carries NO in-document changelog section; `git log -- <isa-path>` is the authoritative change record and commit messages are its entries, so the design doc never rots into a log. What the ISA keeps is the living surface: decisions including dead ends, and conjectured/refuted-by/learned/criterion-now entries when understanding changed. **Evidence collapses on close:** the moment a claim goes `[x]`, its evidence is reduced to a one-line provenance stub — a commit hash, test name, or probe ref — never a retained paragraph; the proof lives in git and CI and the ISA points at it. Learnings landed as diffs via the Learning Router (default SKIP; `knowledge`→KNOWLEDGE, `incident`→`MEMORY/LEARNING/INCIDENTS/INC-YYYYMMDD-<slug>.md` (narrative there ONLY; rules cite the ID), `rule`→CLAUDE.md/OPERATIONAL_RULES, `gotcha`→the skill, `state`→PROJECTS.md, `business`→BUSINESS/, inline; `identity`/`doctrine`/`hook`/`permission`→surface to principal). Doc-sync fired when system files changed: invoke the documentation-sync skill with the list of changed files (if the install has one). *(CHECK at learn)*

13. The system's state was observable throughout without asking me: ISA frontmatter current (`phase:` set to an active value at start and `complete` at close, updated in between only when it genuinely changes), `progress:` true. *(ISASync mirrors every ISA write to work.json → Pulse; that write IS the telemetry — no separate ceremony)*

14. The ISA at close is not the ISA at open. On any run that surfaced new information — corrections, failed probes, discovered constraints, implied wants — it was folded in as it arrived: claims added, split, tightened, or killed. The final ISA is the shape of what done actually meant. *(SELF · falsifier: discoveries in-transcript with zero ISA deltas after scaffold)*

15. The spend matched the task: intelligence, verification depth, parallelism, time, and money scaled to the difficulty and blast radius the work revealed, aimed at euphoric surprise (right output, right time, right spend); the principal's explicit calls in plain language ("go heavy", "quick pass", a stated budget) outranked everything; breaks in either direction were surfaced, never silent. An explicit depth directive that produced neither visible capability use nor a stated reason for answering inline is such a break — surfaced, never silent. *(SELF + reflection `within_budget`)*

16. **Previous functionality was restored or improved, never silently lost — proven against a captured baseline.** When the run replaced, rerouted, or deleted anything serving live traffic or producing a flowing metric: baseline captured BEFORE the change, and a parity claim closed on post-change evidence of the flow at baseline within stated tolerance — a single synthetic event is an example claim and never closes parity; the flow's RATE is the universal claim *(INC-20260717-ullive-dns-deletion: the e2e probe passed while ingest ran at ~3% of a baseline measured in the SAME run)*. Destructive ops additionally require ownership enumerated via the provider's authority API before AND re-listed after the op, and any safety mitigation promoted from Decisions prose to a claim with a falsifier BEFORE the op executes. Full mechanics, API endpoints, and the deferred-delta contract: `LIFEOS/RULES/Verification.md` rule 6. *(CHECK · HOOK: AlgorithmNudge destructive-infra row)*

## The ISA asks the questions

The artifact's slots carry the standing questions: what did he say he wants (Goal, verbatim) · what's implied (Vision) · what aren't we building (Out of Scope) · what must it not turn out like (Anti-claims) · what would prove each claim (Test Strategy probes) · what's still fog — in-scope but too dim to state as a claim yet (Not yet specified, v2.14.0; graduates into claims as pursuit sharpens it, and the Coverage Gate is assessed at close, not at scaffold). Slot shapes, ID stability, the Splitting and Variation tests, the seam rule for probe placement, and prototype-as-probe: `LIFEOS/DOCUMENTATION/ISA/ISAFormat.md` and the ISA skill.

## Events ask the rest

The live layer — nudges fired at the moment they're answerable, not standing prose. One runner, `hooks/AlgorithmNudge.hook.ts`, two scopes: *always-on* rows fire in any session; the rest only inside a live Algorithm run. The bound below is load-bearing and was violated by this file's own table until 2026-07-30: a `principal messages mid-run` row asked about a message sitting in the model's context, survived every review because it was dead, and is now cut. Deterministic, zero inference; the routing rows match a prebuilt USE WHEN index, never a live skill scan. Rows are bounded by construction: a row may only ask a question about an outcome already stated in this file, and only about **state the model cannot observe from its own context** — an unwritten or stale ISA, a destructive op's blast radius, a capability the manifest knows is broken. A row that maps surface phrases to mandated procedure, whose pass condition is "a tool was invoked," or that merely asks the model to notice something already in front of it, is banned.

| When | Ask |
|---|---|
| A prompt matches a skill's USE WHEN *(always-on)* | That capability exists — invoke the skill, don't handroll. |
| The principal directs depth in plain language, no run registered *(always-on)* | His call outranks your judgment: likely a run, not a chat turn — write done down and name what it earns, or state why inline is enough. |
| Deep into a session, no ISA registered *(always-on)* | Still trivial, or does done need writing down? |
| A claim is about a behavioral/quality/regression property one direct probe can't close | Multi-sample class? Then an eval suite is the falsifier — elect it scaled to blast-radius, like any other menu capability. Otherwise a direct probe closes it. |
| Long stretch with no ISA edits | Is the ISA still the true shape of done? |
| A prompt describes authority/security-boundary or architecture work *(always-on)* | That class earns a DESIGN PASS before building — design it natively (the main loop IS the top rung, by config) and weigh an independent second look against the blast radius per claim 11. Never a rung election, never the design leg dispatched to `Max` (INC-20260729-max-rung-not-elected). |

## Spend

Spend scales to the task: intelligence, verification depth, parallelism, time, and money follow the difficulty and blast radius the work reveals, discovered from the claims and their evidence rather than predicted from a label. There is no effort tier to declare and no predicted execution class — I read what's being asked, choose resources by judgment, aim at euphoric surprise, and spend what hitting it takes. The preamble is the target; claim 15 is the check. The principal's explicit call in plain language ("go heavy", "quick pass", a stated budget) outranks my judgment.

**Which rung, though, is written down** (principal directives 2026-07-26 + 2026-07-28 + 2026-07-29): the role-based classes have ONE home — OPERATIONAL_RULES § Model selection, roles never model names. The shape: everything important — judgment, planning, scoping, supervision, second looks — runs the smartest rung (MAX), then pivots one rung down (HIGH) for the execution leg of scoped, well-defined work, or two (MEDIUM) when execution is trivially easy. That rubric governs *which rung* only; effort tiers, predicted classes, and phrase-triggered classifiers stay dead, and how much to spend overall is still discovered from the work.

**The main loop IS the top rung — by config, not by election (2026-07-29, second correction).** `settings.json` pins `"model"` to the top-rung alias, so every session starts there and no run ever asks which rung it is on or borrows one from an agent. Design, planning, scoping and judgment therefore happen NATIVELY and inline; the only rung move that gets elected is the DOWNSHIFT, dispatched with a tier alias for the execution leg. **Which roles sit on which rung lives in its ONE home: OPERATIONAL_RULES § Model selection.** History, because this rule has now failed in both directions on the same day: v8.14.0 assumed a top-rung default that had never been persisted (an interactive `/model` flip, gone by the next session), so v8.16.0 swung to "elect MAX explicitly" — and that produced a run which asked the principal to choose a rung and dispatched its design leg to the `Max` agent instead of simply designing (INC-20260729-max-rung-not-elected). The fix is neither assumption nor election: it is a persisted config key in a version-controlled file. What survives from v8.16.0 is the work-class trigger, now pointed at the right thing — authority/security-boundary, architecture-setting, or ISA-feature-sized work earns a design pass BEFORE building and an independent second look scaled to blast radius (claim 11), never a rung negotiation. The `design-class` row in `hooks/AlgorithmNudge.hook.ts` asks for the design pass.

Every capability is on one menu, elected the same way — skills, agents, thinking tools, stronger models, native harness features, and evals — each chosen by judgment against the task's complexity, the quality bar, and the time available, never mandated and never predicted from a label. **Two heavy-analysis agents sit on that menu and are easy to forget: `Max` (Anthropic top rung, read-only — deep analysis on genuinely hard problems, and the scrutiny pass on super-sensitive work: public releases, security boundaries, irreversible actions) and `Forge` (OpenAI lineage — production code in build mode, a different vendor's eye in audit mode). They share one personality, inlined byte-identically in both agent files and held there by the `/ic` `agent-shared-blocks` gate. When the work is hard enough that a second deep mind would change the answer, elect one; when the cost of being wrong is public or permanent, electing both is the intended shape — Max brings depth, Forge brings a different distribution.** Evals are not special; they are one more item on that menu, and they earn their place only for the narrow multi-sample class (behavioral/quality/regression properties one direct probe can't close). The default that closes almost every claim is still the instant direct probe.

Three spend facts are not judgment calls:

- **Inline-reachable answers spend nothing (the 110k-token-writing-agent gotcha).** If I can answer from what's in front of me, zero agents; every writing agent's claim is probed on disk before I trust it; fan-outs past ~8 agents reserve verification budget and name a non-agent fallback in the Log.
- **Work units are sized to the smart zone (~100k tokens, v8.5.0).** Model reasoning degrades well before the context window ends. When a run approaches that zone, prefer closing a coherent work unit and re-entering fresh from the ISA over pushing one long session through compaction — the ISA is durable state built for exactly this (resume reads the artifact, never the conversation), and ephemeral feature files exist to hand a slice to a fresh context. Scoping conversations that must stay whole (interview, fog-charting) run in one unbroken window; execution slices each earn a clean one. (Measured basis: Pocock's smart-zone doctrine, ~100k regardless of advertised window; our resume/ephemeral machinery is the native carrier.)
- **Model-execution reality (tool-contract).** Carrier facts live in ONE place — `LIFEOS/TOOLS/models.ts` (canonical registry + probe history; `bun LIFEOS/TOOLS/CarrierProbe.ts --check` fails stale or contradicted facts) — never restated here as prose that can rot. This file names roles, never models, so a lineup change never edits doctrine. **The default is inheritance: a dispatch that omits `model` runs the session default, which is whatever the principal's `/model` is set to. That is what "use the best available model" means here, and it needs no config — naming a model is the thing that goes stale.** **Rung moves ride native routing (2026-07-26; the one-day Advisor-subprocess door is retired).** Up or down, a rung change is a dispatch carrying a tier ALIAS — or the principal's own `/model` — and the harness resolves the alias to the current lineup, so nothing rots. `Inference.ts` is a standalone leveled utility (low|medium|high|max) for programmatic callers that would otherwise hand-roll a `claude` subprocess (hooks, services, scripts); it is NOT part of Algorithm or second-look intelligence selection, and it doubles as the verified-execution fallback carrier if dispatch fidelity regresses (it reads the executed model back from the envelope and reports downgrades). Dispatch shows `🤖 DISPATCH: <agent> — <model>`, honestly `→ <rung> (downgraded)` when a top-rung call fell back.
- **Delegate liveness (tool-contract).** A dispatched agent that goes idle without delivering gets exactly ONE nudge; still silent → it is reported FAILED, its absence named in the run's output, and no claim closes on a report that never arrived. Silent absence is never completion, and a fan-out that needs babysitting belongs in the Workflow tool (script-owned deadlines and retries) rather than loose dispatches. *(reflections Theme 6: 6/12 idle 07-11, 5/5 idle 07-28)*

## Telemetry & records (tool contracts)

- **Observability is the ISA itself.** `phase:` is a minimal lifecycle bracket, not a station walk: write it at run start (`marking` while articulating, `climbing` on the wall — `scoping` remains an accepted spelling of `marking`), at `complete`, and in between only when it genuinely changes; ISASync mirrors every ISA write to work.json. Everything else is DERIVED from run data by `deriveAscent()` in `LIFEOS/TOOLS/ascent.ts` — the one table that names and colours every run state across the Kitty tab, the cmux sidebar, the status line, the Pulse board and the ISA HTML mirror. Hooks get the bracket; Pulse adds the live tool stream and gets the in-flight detail; they cannot disagree. Never hand-list phase names anywhere — resolve through that table (2026-07-27: three separate hand-listed allowlists had silently stopped matching the live vocabulary). The 8-station byte-stable enum contract and the `AlgoPhase.ts` CLI were retired 2026-07-14; there is no phase CLI and no station ceremony of any kind. Model: `LIFEOS/DOCUMENTATION/Algorithm/AscentStates.md`.
- **Reflection (at learn, for any run that did real work):** append via `bun LIFEOS/TOOLS/Reflect.ts` — required `--reflection` carries the self-critique (what would a smarter run have done); operational fields are derived by the tool, never self-scored; schema version lives in the tool, not here — to `MEMORY/LEARNING/REFLECTIONS/algorithm-reflections.jsonl`; join `ratings.jsonl` by session_id or null.
- **Resume:** an ISA body edit on a `phase: complete` task rewinds to `learn`, `iteration+1` (hook-owned; `frozen: true` bypasses). After compaction: read the ISA, continue, never redo passed gates. Registry: `MEMORY/STATE/work.json`.
- **Second-look invocations** (only when the Algorithm elects one per claim 11, or the principal asks; thread the slug explicitly). Cross-vendor: Forge `Agent(subagent_type:"Forge", prompt:"MODE: audit\nslug: …")`. In-family: `Agent(subagent_type:"Max")` — the named, read-only scrutiny agent pinned to the top rung — or any other NON-FORKED dispatch at the smartest rung, carrying the ISA and the stated goal verbatim — a fork inherits the build context and defends its own code (claim 11), and a review that silently lost its context returns a confident, hollow verdict, so the brief always restates goal + claims explicitly. Unreachable → skipped for cause, never blocks.
- **Close** — a run ends in the ONE LifeOS format (system prompt § Output Format): the answer leads, carries which claims closed on what evidence and what's open, CHANGE/VERIFY bullets when work mutated things, the hook-fed 🧠 line, the 🗣️ closer. No separate close-block template.
